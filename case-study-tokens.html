01 — The Problem

One Variable. Six Names. Zero Sync.

Designers export tokens from Figma. Developers manually translate to platform formats. CSS needs camelCase. Swift needs PascalCase. Kotlin needs snake_case. Every release, developers spend 2-3 hours fixing naming mismatches.

The design system promises speed. Manual token exports break that promise. Every sync failure erodes trust between design and engineering — and trust, once lost, takes months to rebuild.

The Real Cost

It's not the 2-3 hours. It's the QA cycles that follow. It's the developer who stops trusting the design file and hard-codes values instead. It's the drift that accumulates silently across 6 platforms until someone notices the button color is wrong — in production.

What if we could export once and use everywhere?
02 — Research

The Discovery

I interviewed 4 designers and 6 developers across all 3 platform teams. The question was simple: what's the #1 frustration in design-to-code handoff?

The answer was unanimous — and surprising. Not missing tokens. Not wrong values. Wrong names.

⚙️

"The values are always right in Figma. But by the time they reach my code, the names are different. I spend more time renaming than implementing."

— Frontend Developer, Web Team

The gap isn't between Figma and code. It's between Figma's variable naming conventions and each platform's naming conventions. The translation layer was manual, error-prone, and repeated on every single release.

We knew the pain. Now we needed to define the jobs the solution had to do.
03 — Strategy

Four Core Jobs

From the interviews, four distinct jobs-to-be-done emerged. Each one mapped to a specific failure mode in the current workflow:

  • Filter by Token Type — Colors, spacing, typography, and shadows don't all export the same way. Designers need control over what gets exported, not an all-or-nothing dump.
  • Support Light & Dark Modes — One variable, multiple theme values. Export both in a single pass instead of running the workflow twice and manually merging results.
  • Smart Naming Conventions — Apply camelCase, PascalCase, or snake_case on export. Match platform norms automatically. Never overwrite the Figma source.
  • Sync to Notion — Single source of truth. Designers and developers see the same token data in real-time. No more screenshots of Figma variables in Slack.
Four jobs defined. Time to architect the plugin.
04 — Design

Four Stages. Zero Manual Translation.

The plugin architecture followed a linear pipeline — each stage reducing the chance of error before the next one:

  • Discovery — Read all Figma variables from selected collections automatically. No manual inventory needed.
  • Config — Choose naming convention. Select which modes to include. Set the output format. All decisions in one panel.
  • Preview — See generated code in real-time before export. Catch errors at zero cost. This stage turned out to be the hero.
  • Export — CSS, JS/TS, Flutter, Kotlin, Swift, JSON — all from one plugin. One click. Six platforms.
Why Preview Matters

Every tester in usability sessions said the same thing: the preview panel caught errors they would have missed. Real-time validation eliminates most export bugs before they ship — turning a 2-hour fix into a 2-second glance.

The architecture was sound. But would the controls feel intuitive in practice?
05 — Solution

Every Decision in One Panel

The plugin UI consolidated every export decision into a single screen. No wizards, no multi-step flows — one panel with four control groups:

  • Collections — Select which variable groups to export. Filter by type. Export colors without dragging along every spacing token.
  • Modes — Include light/dark/custom theme variations in a single export. No more running the plugin twice and merging outputs.
  • Naming — camelCase for JS, PascalCase for Swift, snake_case for Python/SQL. Applied on export, not in Figma. The source stays clean.
  • Format — CSS/SCSS variables, JS objects, Dart constants, Kotlin objects, Swift structs, raw JSON. Choose and export.

Smart defaults drove adoption. The plugin defaulted to camelCase for JS projects, snake_case for Python. Less thinking meant more usage — 92% of token releases now go through the plugin pipeline.

Built and designed. But did it actually eliminate the naming problem?

07 — Validation

Usability Testing

Tested with 3 designers and 2 developers before launch. Two findings shaped the final release:

Finding 01

The collection selector needed search for teams with 40+ collections. Scrolling through a flat list didn't scale. Added a search filter that reduced selection time from ~15 seconds to under 3.

Developers also requested CLI export — added to v2 roadmap. The plugin covers 92% of use cases; CLI will cover the remaining 8% for CI/CD pipelines.

Finding 02

The preview panel was the most praised feature. Every tester said it caught errors they would have missed. One developer described it as the single reason they trusted the plugin over their previous manual process.

08 — Reflection

Five Technical Lessons

01 — Preserve original casing.

Store token names as-is in Figma. Apply conventions only at export. Never overwrite the source. The moment you mutate the source, you lose the ability to export to a different convention later.

02 — Test multi-segment names.

"color-primary-hover-dark" exposes casing logic bugs. Test edge cases early — they're the names that break in production, not the simple ones.

03 — Preview catches errors.

Real-time validation eliminates most export bugs before they ship. The cost of showing a preview is near-zero. The cost of not showing one is a QA cycle.

04 — Proxy simplifies CORS.

A local server handles Notion API auth. Eliminates cross-origin headaches that would have blocked the sync-to-Notion feature entirely.

05 — Smart defaults win adoption.

Default camelCase for JS, snake_case for Python. Less thinking means more adoption. The plugin that requires zero configuration on first use is the plugin that gets used.
