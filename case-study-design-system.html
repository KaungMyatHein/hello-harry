01 — The Problem

The Breaking Point

The brand green changed. A simple hex value update. The team spent two days manually updating components across every platform file. QA still found 14 screens they missed.

Three products shared one Figma file: POS for cashiers, Web dashboard for managers, Mobile for staff. Three radically different interaction models — touch targets, information density, gesture patterns — all crammed into a single library.

The shared file was supposed to keep things consistent. Instead, it became the single point of failure. Every change rippled unpredictably. Every new designer asked the same question on day one.

"I don't know which file is right."

— New designer, day 3 of onboarding
That file was the problem. But what would the solution look like?
02 — Audit

What the Audit Revealed

I ran three audits — tokens, components, and team interviews. Each one told the same story: drift at every level.

Token Audit

47 duplicate color values. The brand primary had drifted 2-6 shades from spec — a different hex in POS, Web, and Mobile. Nobody noticed because nobody had a single source to check against.

Component Audit

31 near-duplicate components. Fixing one never fixed the others. Button height: 48px in POS, 36px in Web, 44px in Mobile. Three teams, three interpretations of "the same button."

Team Interviews

New designers took 3 days to onboard — most of that time spent figuring out which components were current and which were abandoned. Tribal knowledge replaced documentation.

The root cause was clear: one shared library doesn't scale for three radically different surfaces.

03 — Strategy

Old vs. New Mental Model

Old Model: One library for all platforms. Fast to start. Catastrophic to maintain. Every change ripples unpredictably because there's no separation between shared foundations and platform-specific needs.

New Model: Foundation + Platform layers. A shared core that defines what's universal — then platform libraries that extend without redefining the foundation. Changes flow down, never sideways.

The Architecture

Level 1 — Global Foundation: Raytail Style Guidelines. Primitives, Typography, Brand, Base Logic. Published once. Consumed by all three platform libraries.

Level 2 — Platform Libraries: POS gets 48px touch targets and dark surfaces. Web gets light surfaces and dense tables. Mobile gets gesture-aware components and bottom sheets. Each extends the foundation — none redefine it.

04 — Token Architecture

Three Tiers. Zero Ambiguity.

The token system needed to be strict enough to prevent drift, but flexible enough to support three different surfaces. We designed a three-tier model:

  • Tier 1 — Reference — Raw primitives. color/green/500: #1B7A4A. Never used in components directly. These are the atomic building blocks that only semantic tokens reference.
  • Tier 2 — Semantic — Named by intent. action/primary resolves differently per platform. surface/base is #0D0E0F on POS, #FFFFFF on Web. Same name, appropriate value.
  • Tier 3 — Component — Scoped overrides. button/bg/primary points to action/primary. Reskin without touching globals. The escape hatch that never breaks the system.

The three-tier model meant a brand color change was now a single token update at Tier 1. It propagated through semantic and component tokens automatically. No manual hunt. No missed screens.

With tokens defined, how did platform-specific decisions shape each product?
05 — Platform Decisions

POS: Design for the Shop Floor

The POS had the most extreme constraints. Every design decision was shaped by the physical environment — retail lighting, touch hardware, transaction speed, and the cost of errors.

Components defined. But who owns what — and how do we prevent drift from returning?
06 — Components

Atoms, Molecules, Organisms

The component strategy followed the same two-level split as the architecture: global atoms owned by the foundation, platform molecules and organisms owned by each team.

  • Atoms (Global) — Color, Type Scale, Icon Set, Spacing, Radius, Shadow. Defined once. Inherited everywhere. No platform can redefine these.
  • Molecules (Platform) — POS: Numpad, Transaction Row. Web: Data Table, Filter Chip. Mobile: List Item, Bottom Sheet. Each platform builds what it needs from shared atoms.
  • Organisms (Platform) — POS: Transaction Panel, Product Grid. Web: Analytics Header, Inventory Table. Complex compositions that only make sense in their platform context.
The system was built. Now it needed rules to stay alive.
07 — Governance

Rules That Prevent Drift

A design system without governance is a wiki that nobody reads. We established four rules — each one addressing a specific failure mode from the old model:

  • Foundation Team owns Level 1. Breaking changes require cross-team coordination. No silent updates.
  • Platform Teams own Level 2. Can add components freely. Cannot redefine global tokens. Gaps become proposals, not workarounds.
  • Naming Convention: category/property/variant. Enforced globally. Inconsistent naming is the #1 cause of drift.
  • Docs live in Figma. Documentation that drifts from the component is worse than no documentation. If the doc isn't attached to the component, it doesn't exist.

The critical rule: global token updates sync all platforms on publish. Manual propagation is architecturally impossible. The system enforces consistency — it doesn't rely on discipline.

09 — Resolution

The Green Changed Again

Brand primary green changed again. This time: one token update. Every screen across POS, Web, and Mobile reflected it by end of day. QA flagged zero inconsistencies.

The same change that took two days and missed 14 screens now took minutes and missed nothing. The system shifted from designer overhead to a strategic asset.

10 — Reflection

What I Would Revisit

01 — Motion Tokens.

Left out of v1. Platform teams implemented animations independently — creating jarring inconsistencies that only surfaced at QA. Motion should have been a foundation-level concern from the start.

02 — Accessibility Tokens.

Minimum contrast ratios should be token constraints, not designer knowledge. If the system can't enforce accessibility, it relies on individual awareness — which doesn't scale.

03 — Component Status.

Without stable / experimental / deprecated labels, teams consumed experimental components and hit breaking changes. Status metadata prevents teams from building on unstable foundations.

04 — Theming Architecture.

The two-level model supports white-labeling — but only if semantic tokens never reference raw hex directly. This constraint needs to be enforced architecturally, not documented.
