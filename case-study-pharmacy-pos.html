01 — The Problem

From Windows to Touchscreen

STO's pharmacy and supermarket chains were running on a legacy Windows-based POS. Clunky, mouse-driven, built for desktops — not for the fast-paced counter environment where every second counts.

The goal: redesign the entire system for touchscreen POS devices. Not a port — a complete UX rethink. 14 modules, 200+ screens, one designer.

Before I touched UI, I found a process problem bleeding time across every module.

04 — Deep Dive · Login

Use the Card They Already Carry

The problem. The old Windows POS opened on a username/password screen. Cashiers shared logins to skip it. Audit trail broken on day one. The IS team wanted hardened auth; the cashiers wanted to start scanning groceries inside 10 seconds.

The constraint that unlocked the decision. Every cashier already carried an NFC staff card for the building turnstile. The hardware on the new touchscreen POS terminal had an NFC reader built in. No new credential to issue, no extra cost, no behaviour change to teach — just point the existing card at a different surface.

Before
After

What I designed. Tap-to-login as the primary path, with a manual employee-code fallback for lost/forgotten cards and a forced float-declaration step before the register opens. The fallback exists because hardware fails — but it's the slow path, not the default.

  • NFC card tap — reuse the existing staff badge. Auth in <2s. Audit trail per cashier, not per terminal.
  • Manual fallback — employee code + pincode via on-screen keyboard. Slow on purpose so it isn't the habit.
  • Float gate — drawer-count required before checkout opens. Compliance Team requirement; surfaced as a single screen, not a popup chain.
09 — Deep Dive · E-Prescription

Friction Where It Belongs

The problem. A pharmacy cashier scans a prescription. The system detects two drugs that overlap dangerously. In the old POS, a warning popup appeared and could be dismissed with one tap of "OK". Compliance flagged this: every override left no record of why.

The two options on the table.

Option A
Hard block
Refuse the sale outright when the system detects an overlap. Pharmacist must remove the conflict before continuing.
Option B ✓
Override + mandatory reason
Allow the sale, but force the pharmacist to type a free-text reason. No skip, no preset dropdown, no "OK" button until the text field has content.

Why Option B. Hard blocks treat the cashier as a hazard. Real pharmacy work has legitimate overrides — a doctor authorising a known interaction, a refill for a patient already stable on the combo. The Compliance Team's actual need wasn't to prevent overrides; it was to make every override auditable. Friction is the audit trail.

  • Drug overlap — typed reason required, minimum 10 chars. Submit button disabled until satisfied.
  • Partial fulfillment — pharmacy can dispense 3 of 5 items now, leave 2 open. Status sticks to the prescription, not the transaction.
  • Pharmacy-only — module hidden in supermarket-mode terminals. Same codebase, contextual surfacing.
12 — Deep Dive · Tender Operations

One Payment at a Time, Not All at Once

The problem. Ten payment types: Cash MVR, Cash USD, Cards, BNPL, BML, Ooredoo, Insurance, Cheques, Coupon, Loyalty. Some transactions take two of these (rare), most take exactly one. The old POS dropped everything into one dense form regardless.

The two options on the table.

Option A ✓
Separate screen per payment type
Cashier picks the type first, then sees a screen tuned only to that type. To split, they finish one, then start another against the remainder.
Option C
Unified split-tender canvas
All ten payment fields visible at once. Cashier fills any combination in one screen and submits.

Why Option A. Two reasons, both anchored in how cashiers actually think:

  • Split tender is rare. Most transactions are one payment, full amount. Optimising the screen for the common case (1 method) is the right tradeoff — a unified canvas makes the 90% case slower so the 10% case is faster.
  • Cashiers think one payment at a time. Watching shifts, I saw the verbal pattern: "that's 240 on cash" → counts → "and the rest on card". The screen should mirror the speech, not contradict it. Option C asks the cashier to hold the whole split in their head before any field is filled.
Before
After

What I designed. A picker grid of 10 payment tiles → one focused screen per type → a persistent "remaining balance" header that updates as each payment posts. Split tender becomes a loop of single payments, not a parallel form.

  • 10 payment types — one reusable screen component, configured by type. Cash MVR/USD has denomination buttons; Cards has terminal-reference field; Cheque has bank + serial.
  • Split tender — sequential, not parallel. Remaining balance always visible at the top.
  • One component pattern — adding an 11th payment type later is a config change, not a redesign.

19 — Reflection

What I Learned

01 — Fix the process first.

Prototype-on-hardware saved more time than any UI change.

02 — Design for the harder context first.

You can remove guardrails. You can't bolt them on.

03 — Consistency at scale is structural.

The repeatable 6-page file structure held 200+ screens together.

04 — Stakeholder buy-in is a deliverable.

Comic storyboards got BNPL funded. Design for decision-makers too.
