01 — Problem

From Windows to touchscreen.

STO's pharmacy and supermarket chains were running on a legacy Windows-based POS. Clunky, mouse-driven, built for desktops — not for the fast-paced counter environment where every second counts.

The goal: redesign the entire system for touchscreen POS devices. Not a port — a complete UX rethink. 14 modules, 200+ screens, one designer.

A port would have shipped faster. It would also have failed: a Windows form ported to a touch screen still expects pixel-precise clicks, hover states, keyboard tab order. The pharmacy counter has none of those things — only a 15-inch screen, a busy cashier, and a queue that doesn't care.

Before I touched UI, I found a process problem bleeding time across every module.

02 — Discovery

The rework trap.

Devs were building on designs the IS Team hadn't approved. Every module hit the same loop: build, review, rework.

I mapped three workflows side by side — ideal, actual, and proposed — to make the waste visible. The actual workflow had a feedback loop the size of a feature. The proposed one cut that loop out by moving validation upstream.

I then proposed putting Figma prototypes on the actual POS hardware — IS Team confirmed on the real device before any code was written. This single change saved more time than any UI decision I made on the entire project.

User Flows

How it all connects.

Every module started as a FigJam flow before any UI was designed — happy paths, edge cases, and decision points mapped first.

The discipline was simple: no Figma frame got drawn until the flow had a confirmed start state, a confirmed end state, and at least three branch points in between. This caught the seams between modules — login handing off to checkout, checkout handing off to tender — before the seam became a UI bug.

04 — Deep Dive · Login

Use the card they already carry.

The old Windows POS opened on a username/password screen. Cashiers shared logins to skip it. Audit trail broken on day one.

The problem. The IS team wanted hardened auth; the cashiers wanted to start scanning groceries inside 10 seconds. The existing flow gave neither side what they needed.

The constraint that unlocked the decision. Every cashier already carried an NFC staff card for the building turnstile. The hardware on the new touchscreen POS terminal had an NFC reader built in. No new credential to issue, no extra cost, no behaviour change to teach — just point the existing card at a different surface.

Before · legacy Windows
After · NFC tap-to-login

What I designed. Tap-to-login as the primary path, with a manual employee-code fallback for lost/forgotten cards and a forced float-declaration step before the register opens. The fallback exists because hardware fails — but it's the slow path, not the default.

  • NFC card tapReuse the existing staff badge. Auth in <2s. Audit trail per cashier, not per terminal.
  • Manual fallbackEmployee code + pincode via on-screen keyboard. Slow on purpose so it isn't the habit.
  • Float gateDrawer-count required before checkout opens. Compliance Team requirement; surfaced as a single screen, not a popup chain.
09 — Deep Dive · E-Prescription

Friction where it belongs.

A pharmacy cashier scans a prescription. The system detects two drugs that overlap dangerously. In the old POS, a warning popup appeared and could be dismissed with one tap of "OK". Compliance flagged this: every override left no record of why.

The two options on the table.

Option A Hard block

Refuse the sale outright when the system detects an overlap. Pharmacist must remove the conflict before continuing.

Option B · picked ✓ Override + mandatory reason

Allow the sale, but force the pharmacist to type a free-text reason. No skip, no preset dropdown, no "OK" button until the text field has content.

Why Option B. Hard blocks treat the cashier as a hazard. Real pharmacy work has legitimate overrides — a doctor authorising a known interaction, a refill for a patient already stable on the combo. The Compliance Team's actual need wasn't to prevent overrides; it was to make every override auditable. Friction is the audit trail.

Surface · E-Prescription override
  • Drug overlapTyped reason required, minimum 10 chars. Submit button disabled until satisfied.
  • Partial fulfillmentPharmacy can dispense 3 of 5 items now, leave 2 open. Status sticks to the prescription, not the transaction.
  • Pharmacy-onlyModule hidden in supermarket-mode terminals. Same codebase, contextual surfacing.
12 — Deep Dive · Tender Operations

One payment at a time, not all at once.

Ten payment types: Cash MVR, Cash USD, Cards, BNPL, BML, Ooredoo, Insurance, Cheques, Coupon, Loyalty. Some transactions take two of these (rare), most take exactly one. The old POS dropped everything into one dense form regardless.

The two options on the table.

Option A · picked ✓ Separate screen per payment type

Cashier picks the type first, then sees a screen tuned only to that type. To split, they finish one, then start another against the remainder.

Option C Unified split-tender canvas

All ten payment fields visible at once. Cashier fills any combination in one screen and submits.

Why Option A. Two reasons, both anchored in how cashiers actually think:

  • Split tender is rareMost transactions are one payment, full amount. Optimising the screen for the common case (1 method) is the right tradeoff — a unified canvas makes the 90% case slower so the 10% case is faster.
  • Cashiers think one payment at a timeWatching shifts, I saw the verbal pattern: "that's 240 on cash" → counts → "and the rest on card". The screen should mirror the speech, not contradict it. Option C asks the cashier to hold the whole split in their head before any field is filled.
← Drag to compare →
Before · dense form
After · picker + focused screen

What I designed. A picker grid of 10 payment tiles → one focused screen per type → a persistent "remaining balance" header that updates as each payment posts. Split tender becomes a loop of single payments, not a parallel form.

  • 10 payment typesOne reusable screen component, configured by type. Cash MVR/USD has denomination buttons; Cards has terminal-reference field; Cheque has bank + serial.
  • Split tenderSequential, not parallel. Remaining balance always visible at the top.
  • One component patternAdding an 11th payment type later is a config change, not a redesign.

05 — Reflection

What I learned.

Four lessons that survived the project and that I'd carry into the next enterprise system without question.

Lesson 01 Fix the process first

Prototype-on-hardware saved more time than any UI change. The cost was a few hours per module. The savings were entire rework cycles — and the trust that came from IS Team confirming on a real device.

Lesson 02 Design for the harder context first

You can remove guardrails. You can't bolt them on. Pharmacy compliance (mandatory reason, supervisor auth) shaped the patterns; the supermarket simply inherited them without the friction.

Lesson 03 Consistency at scale is structural

The repeatable 6-page file structure held 200+ screens together. Same headers, same nav, same auth pattern, same component library — applied 14 times.

Lesson 04 Stakeholder buy-in is a deliverable

Comic storyboards got BNPL funded. Design for decision-makers too — they don't read specs, they look at pictures and ask "can we afford this?"
