The bottleneck isn't the artifact. It's the handoff.

Most AI design tools speed up one phase — PRDs in Notion AI, screens in Figma AI, code in Cursor. None of them fix the part that actually slows teams down: the handoff between phases, where intent leaks and context dies. Agent Harry is built around the opposite bet — design the AI for the handoffs, not the tasks.

01 — Problem

AI fixed the artifacts. It didn't fix the seams.

Notion AI writes the PRD faster. Figma AI generates screens. Cursor writes code. v0 builds prototypes. Each tool helps one phase. None of them help the part that actually slows teams down.

A PRD doesn't slow a team down when the PM writes it. It slows the team down the moment a designer reads it and starts guessing at the parts that aren't written.

The same is true at every boundary: PRD to lo-fi sketch · lo-fi to hi-fi · hi-fi to engineering implementation. Context leaks at every step. Intent gets lost. AI today writes the PRD faster — but it does not fix the guessing.

The hard part of product work isn't the individual artifact. It's the connective tissue between phases.
02 — Reframe

Stop building AI tools. Build AI teams.

The conventional way to design an AI agent system is to treat it as software — spec the agents, define their APIs, wire them up. That's the wrong mental model.

An AI agent system is closer to a team than to a piece of software. A team has roles, but the roles aren't the hard part. The hard part is how the team communicates, where it meets, who pushes back on whom.

When I started thinking about Agent Harry as a team instead of a toolkit, three design questions emerged that I had not been asking:

Q1 How do agents hand off work?

The protocol between phases — not the prompts inside them — is where speed comes from.

Q2 Where does the team meet?

A team without a canonical surface defaults to chaos. Chat or dashboard? Pick one.

Q3 Who tells the team when it's wrong?

A team without a critic ships its mistakes. Quality is structural, not aspirational.

This case study walks through the first two moves. The third — the critique partner — deserves its own essay.

04 — Move 1

Designing the handoffs.

The protocol that travels with the work — so no agent has to guess what success looks like.

Industry today vs Agent Harry

Industry today PRD → guess → guess → guess

PM writes a PRD in Notion. Designer reads it, sketches lo-fi in FigJam, builds hi-fi in Figma. Engineer opens Dev Mode, jumps to Cursor. Each handoff is a human guessing at the previous human's intent. AI tools speed up the artifacts. They don't fix the guessing.

Agent Harry The journey is the contract

Every PRD emits a structured journey: persona · entry condition · success exit · failure exit. lo-fi reads the journey. figma reads the journey. design-engineer reads the journey. By the time work reaches code, every agent has the same definition of "what does success look like."

The point isn't that AI writes faster. The point is that AI agents can be designed to refuse context loss — something human teams cannot enforce. The journey is the smallest object that, once everyone reads from it, makes the seams disappear.

Most AI tools today are point solutions for individual phases. The real leverage is designing AI for the handoffs, not the phases.
05 — Move 2

Designing where the team meets.

If a team has two places to look, it has none. Chat is the surface — and that's an org decision before it's a UX one.

Two surfaces compared

Dashboard pattern LangChain / AutoGPT style

Agent cards. Run buttons. Status panels. Logs viewer. The default assumption: if you have agents, you need a dashboard to control them. Built like every other industry tool — because dashboards are what we know.

Chat-only pattern Agent Harry / Claude Code style

No dashboard at all. Every agent decision — a journey, a PRD section, a Figma spec, a handoff doc — renders as chat markdown. The user sees agent output in the same surface they'd see a teammate's message. There is no second place to look.

This sounds like a UX simplification. It is actually an org design decision. When chat is canonical, the team has one place to meet. A dashboard would be a second one — and for a team that already lives in the conversation, one is enough.

People meet where the conversation is, not where the buttons are.

06 — Shipped

SF-35: the proof.

A ⌘K spotlight modal for patient search across three clinic branches. Built end-to-end by the pipeline — no Figma file was opened.

The receptionists are Burmese, and they search by phone number before they say a name. The feature had to handle Burmese honorifics — Daw, U, Ma, Ko — that English search libraries strip incorrectly. It had to fall back across branches when a patient wasn't local. It had to ship into a production header.

From kickoff to shipped code: 1 hour 53 minutes. The same feature, in a traditional Figma → engineer handoff, takes 2.5 to 5.5 days. That's a 10–25× speedup, depending on the phase.

07 — Lessons

Four lessons.

Lesson 01

The handoff is the team's communication protocol.

Most AI tools today are point solutions for individual phases. The real leverage is designing the contract that travels with the work — so no agent has to guess what success looks like.

Lesson 02

People meet where the conversation is.

Dashboards feel like the default because that's what every other tool looks like. But a team that already lives in the conversation needs one place to meet, not two.

Lesson 03

A team without a critic ships its mistakes.

critique-partner caught a fake DB relationship, a useEffect race, and the Burmese honorifics gap — across four rounds. Quality is structural, not aspirational.

Lesson 04

Structure beats horsepower.

The same model, wrapped in the same prompts, with a different protocol — produces a radically different system. Agent Harry's edge is org design, not model choice.
